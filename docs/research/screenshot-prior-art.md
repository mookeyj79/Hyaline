# How other theme projects shoot and frame screenshots

Research for [issue #38](https://github.com/mookeyj79/Hyaline/issues/38), part of the map in [issue #36](https://github.com/mookeyj79/Hyaline/issues/36). Read on 2026-11-15. Primary sources only: each project's own repo, docs, and source code. Each claim links to the file that owns it.

Three labels are used throughout:

- **Documented**: the linked doc or source says it.
- **Measured**: read from a file here (image size, format), not stated by the project.
- **Undocumented**: the project does not say. Nothing here is guessed.

## Short answer

1. **Nobody automates the capture of real apps.** In all five projects, a person takes the port screenshot by hand. The only automation found renders web pages with a headless browser, never a native app. Hyaline's pipeline has no prior art to copy for the capture step.
2. **Only Catppuccin has a framing tool**, `catwalk`. It joins exactly four same-size images into one, with rounded corners. It adds no backdrop, no padding around a single image, and no shadow, and it cannot take two images.
3. **The well-known "pretty screenshot" tools do not take a screenshot as input.** `freeze`, `vhs`, `silicon`, `termshot`, Carbon, and ray.so each draw code or terminal text themselves. They cannot frame a capture of a real app, and using them for a port would be a mock.
4. **ImageMagick does the whole framing step.** A recipe was run here on two Hyaline captures: wallpaper backdrop, padding, rounded corners, one soft shadow, and a Dark and Light pair. A pixel comparison showed the window interior is unchanged. See [A tested ImageMagick recipe](#a-tested-imagemagick-recipe).

So Hyaline reuses the **conventions** from other themes (one image per variant, same size, fixed file names, an optional combined image) and the **tool** from ImageMagick.

## How the theme projects do it

### Catppuccin

- **Rules.** The port guide says: "Put the images under `assets/`", "Prefer `.webp` over `.png` for images", and "The main preview image should be an image generated by catwalk". It calls catwalk "an essential tool" that makes "a layered screenshot of your port which combines all four flavors into one". Documented: [port-creation.md](https://github.com/catppuccin/catppuccin/blob/main/docs/port-creation.md).
- **Layout.** The port template README shows `preview.webp` at the top, then a "Previews" section with one collapsed `<details>` block per flavor: `latte.webp`, `frappe.webp`, `macchiato.webp`, `mocha.webp`. Documented: [template README](https://github.com/catppuccin/template/blob/main/README.md).
- **Capture.** Undocumented. Neither the port guide nor the template says how to take the four screenshots, at what size, or with what sample content.
- **Size.** Not set. Measured on the VS Code port: each flavor image is 2950x1964 WebP with alpha, and `preview.webp` is 6064x3928 lossless WebP with alpha ([assets](https://github.com/catppuccin/vscode/tree/main/assets)).
- **CI.** One repo automates previews: [vscode-icons previews.yml](https://github.com/catppuccin/vscode-icons/blob/main/.github/workflows/previews.yml). Its [script](https://github.com/catppuccin/vscode-icons/blob/main/scripts/catwalk.ts) writes an HTML page of icons per flavor, screenshots it with Puppeteer (700x400 viewport, device scale factor 3), runs catwalk, and opens a pull request with `peter-evans/create-pull-request`. It is a web page, not an app, but the shape (render, frame, open a PR) is the one Hyaline wants. A [setup-catwalk](https://github.com/catppuccin/setup-catwalk) action installs catwalk on a runner.
- **Not a screenshot pipeline.** The VS Code port runs [Chromatic](https://github.com/catppuccin/vscode/blob/main/.github/workflows/chromatic.yml) on a Storybook of code samples. That is visual regression testing of a mock, not README screenshots.

### Dracula

- **Rules.** The port template has a `screenshot.png` at the repo root, shown at the top of the README. A `screenshot/` folder turns it into a gallery on draculatheme.com. Documented: [template README](https://github.com/dracula/template/blob/main/README.md) and [SCREENSHOT.md](https://github.com/dracula/template/blob/main/screenshot/SCREENSHOT.md).
- **Variants.** The folder is the documented place for "Light and dark variants (Dracula and Alucard)". Images sort by file name, so ports use number prefixes (`01-overview.png`).
- **Formats.** `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`. Documented in SCREENSHOT.md.
- **Tips, quoted.** "Use consistent dimensions across screenshots when possible." "Crop to the relevant UI area instead of capturing the entire desktop." "Keep images reasonably sized".
- **Sample content.** The template ships a `sample/` folder of code snippets in about 25 languages "to help you create consistent screenshots across themes". This is the one project that standardizes what is on screen. Documented: [sample/](https://github.com/dracula/template/tree/main/sample).
- **Capture and framing.** By hand. No tool is named, and no size is set. Measured: the template's own `screenshot.png` is 7680x4320, and the VS Code port's is 1010x1046, so sizes vary widely in practice.
- **The contribute page** covers the palette and how to submit a repo. It says nothing about screenshots. Documented: [draculatheme.com/contribute](https://draculatheme.com/contribute).

### Nord

- **Rules.** Undocumented. The org's [contributing.md](https://github.com/nordtheme/.github/blob/main/contributing.md) mentions screenshots only as attachments to bug reports and pull requests.
- **Where images live.** Port READMEs link to images in the website repo, not the port repo: `nordtheme/web/assets/images/ports/<port>/`. Documented by the links in the [VS Code port readme](https://github.com/nordtheme/visual-studio-code/blob/develop/readme.md).
- **Conventions, measured.** A designed hero image (`repository-hero.png`, 888x600, with a `-2x` twin for high-density screens) and UI overview captures (`ui-overview-jsx.png`, 2650x1389, PNG with alpha).
- **Capture and framing.** Undocumented. No script or workflow for it was found in the port repo or the org docs.

### Rosé Pine

- **Rules.** The port template README has a "Gallery" section with one heading and one image per variant (Rosé Pine, Moon, Dawn). The images are GitHub attachment uploads (`github.com/user-attachments/...`), not files in the repo, set to `width="256"`. Documented: [rose-pine-template README](https://github.com/rose-pine/rose-pine-template/blob/main/README.md).
- **Capture and framing.** Undocumented. The template's [TODO.md](https://github.com/rose-pine/rose-pine-template/blob/main/TODO.md) lists a name, description, topics, license, and README, and nothing about screenshots. The org [CONTRIBUTING.md](https://github.com/rose-pine/.github/blob/main/CONTRIBUTING.md) does not mention them.
- **Social image.** TODO.md points to a "Rosé Pine Images" web app for the repo's social card. That is a title card, not a screenshot. Its source repo was not found under the org (see [Not verified](#not-verified)).
- **Automation.** The template is built with their `bloom` tool, which generates theme files only.

### Tokyo Night

- **VS Code theme.** Three PNGs in `static/`, one per variant (`ss_tokyo_night.png`, `ss_tokyo_night_storm.png`, `ss_tokyo_night_light.png`), stacked under a "Screenshots" heading. The only stated convention: "Font used in the screenshots is JetBrains Mono." Documented: [README](https://github.com/tokyo-night/tokyo-night-vscode-theme/blob/master/README.md). Measured: 1406x979, PNG, no alpha.
- **Neovim theme.** [folke/tokyonight.nvim](https://github.com/folke/tokyonight.nvim/blob/main/README.md) embeds GitHub attachment uploads, one per style. No image files, scripts, or workflow for screenshots are in the repo.
- **Capture and framing.** Undocumented in both.

## What the conventions add up to

Things at least two projects do, which Hyaline can adopt without argument:

- **One image per variant, with a fixed file name.** Catppuccin (`<flavor>.webp`), Tokyo Night, Rosé Pine. Hyaline already has `dark.png` and `light.png`.
- **All variants the same size.** Catppuccin needs it (catwalk fails otherwise), Dracula advises it.
- **Same content in every variant.** Dracula ships sample files for it. Catppuccin's combined image only works if the four shots line up.
- **Crop to the window, not the desktop.** Dracula says so. Catppuccin's and Tokyo Night's images are window crops.
- **An optional combined image for the top of the README**, with the single images below. Catppuccin does this. Dracula uses a gallery instead.
- **Transparent corners.** Catppuccin's and Nord's images carry alpha, so rounded corners show the page behind them. None of the five puts a wallpaper behind the window in its convention. A backdrop is a Hyaline choice, not prior art.

Nobody sets a pixel size, a padding, a corner radius, or a shadow in writing. The later ticket picks those with no standard to follow.

## Framing and capture tools

"Takes a capture" means the tool accepts an existing image as input. Only those can frame a real app screenshot.

| Tool | What it does | Input | Output | Takes a capture | License |
|---|---|---|---|---|---|
| **catwalk** | joins four images, rounds corners | 4 PNG or WebP, same size | PNG or WebP | yes | MIT |
| **ImageMagick** | general image compositing | any image | any image | yes | ImageMagick License |
| **freeze** | draws code or terminal output | source file or ANSI text | SVG, PNG, WebP | no | MIT |
| **vhs** | scripts and records a terminal | `.tape` script | GIF, MP4, WebM, PNG | no | MIT |
| **silicon** | draws code | source file | PNG | no | MIT |
| **termshot** | draws a command's output | a command | PNG | no | MIT |
| **Carbon** | draws code (web app) | pasted code | PNG, SVG | no | MIT |
| **ray.so** | draws code (web app) | pasted code | image | no | MIT |
| **shot-scraper** | screenshots web pages | URL | PNG, JPG | captures, does not frame | Apache-2.0 |
| **Puppeteer, Playwright** | drive a browser | script | PNG | captures, does not frame | Apache-2.0 |
| **scrot, maim, ImageMagick `import`** | grab an X11 screen or window | a display | PNG | captures, does not frame | MIT-style, GPL-3.0, ImageMagick |

### catwalk

- **What.** "Catwalk makes it easy to generate beautiful preview images for your ports." Source: [README](https://github.com/catppuccin/catwalk/blob/main/README.md).
- **Input.** Four images, in the order Latte, Frappé, Macchiato, Mocha. The count is fixed in the code (`images: Option<[Image<Rgba>; 4]>`) and all four must be the same size, or it returns "Images must be the same size". Source: [lib.rs](https://github.com/catppuccin/catwalk/blob/main/src/lib.rs).
- **Layouts.** `composite` (default: four diagonal slices of one window), `stacked` (overlapping cascade), `grid` (2x2), `row` (1x4). Options: `--radius` (percent, default 3), `--gap` (grid and row only, default 50 px).
- **What it does not do.** No shadow, no backdrop (the canvas is transparent), no padding other than the grid gap, no resize. There is no two-image mode.
- **Install.** `cargo install catppuccin-catwalk`, Homebrew tap, Nix, or release binaries for Windows, macOS, and Linux. A WebAssembly build is in `pkg/`.
- **License.** MIT.
- **Fit for Hyaline.** Poor. Two variants do not fit four slots. The Catppuccin plymouth port passes the same image four times to use catwalk only for rounding ([justfile](https://github.com/catppuccin/plymouth/blob/main/justfile)), which shows the workaround and its limits. The `composite` slice idea (Dark on the left, Light on the right of one window) is worth knowing as a layout, and ImageMagick can do it with a mask.

### Charm freeze

- **What.** "Generate images of code and terminal output." Input is a source file, piped text, or `--execute "<command>"`, which captures the command's ANSI output. Source: [README](https://github.com/charmbracelet/freeze/blob/main/README.md).
- **Framing options.** `--background`, `--margin`, `--padding`, `--border.radius`, `--border.width`, `--shadow.blur`, `--shadow.x`, `--shadow.y`, `--window` (macOS-style controls). These are the same knobs Hyaline's framing needs, so its defaults are a useful reference for the look.
- **Output.** SVG, PNG, WebP.
- **Install.** Homebrew, Go (`go install github.com/charmbracelet/freeze@latest`), Debian and RPM packages, release binaries.
- **License.** MIT.
- **Fit for Hyaline.** None for framing. It has no image input: it re-draws text with its own renderer and font. A freeze image of a terminal port would be a mock of that terminal.

### Charm vhs

- **What.** Runs a `.tape` script of keystrokes in a terminal and records it. A `Screenshot <file>.png` command "captures the current frame". Source: [README](https://github.com/charmbracelet/vhs/blob/main/README.md).
- **How it renders.** "VHS requires `ttyd` and `ffmpeg`". The terminal on screen is vhs's own, not the app being themed.
- **Framing options.** `Set Margin`, `Set MarginFill`, `Set BorderRadius`, `Set WindowBar`, `Set Padding`.
- **Output.** GIF, MP4, WebM, a folder of PNG frames, or a single PNG.
- **Install.** Homebrew, apt and yum repos, Go, or Docker: `docker run --rm -v $PWD:/vhs ghcr.io/charmbracelet/vhs <cassette>.tape`. There is a GitHub Action, `charmbracelet/vhs-action`.
- **License.** MIT.
- **Fit for Hyaline.** None for capture or framing, for the same reason as freeze. Two ideas carry over: a small script file per recording (Hyaline's "one small recipe file" per port), and shipping the whole tool as one Docker image.

### silicon

- **What.** "Create beautiful image of your source code." Input is a source file or the clipboard. Source: [README](https://github.com/Aloxaf/silicon/blob/master/README.md).
- **Framing options.** `--background`, `--shadow-color`, `--shadow-blur-radius`, `--no-window-controls`. A transparent background is allowed.
- **Install.** `cargo install silicon`, Homebrew, pacman. Needs system font libraries on Linux.
- **License.** MIT. Last push 2024-09-26.
- **Fit for Hyaline.** None. Code renders only.

### termshot

- **What.** "Creates screenshots based on terminal command output". Draws the output with a window frame and shadow (`--no-decoration`, `--no-shadow`, `--margin`, `--padding`). Source: [README](https://github.com/homeport/termshot/blob/main/README.md).
- **License.** MIT. Install by Homebrew tap or Go.
- **Fit for Hyaline.** None. Same limit as freeze.

### Carbon and ray.so

- **What.** Web apps that draw pasted code as an image. Carbon exports PNG and SVG ([README](https://github.com/carbon-app/carbon/blob/main/README.md)). Carbon's README lists a community CLI, [carbon-now-cli](https://github.com/mixn/carbon-now-cli), which drives the site in a browser. [ray.so](https://github.com/raycast/ray-so) is the Raycast equivalent.
- **License.** Both MIT.
- **Fit for Hyaline.** None. Code renders only, and both depend on a hosted site.

### ImageMagick

- **What.** A command-line image toolkit. The parts framing needs are all documented in its usage guide:
  - Rounded corners by masking the alpha channel: [Rounded and Shaped Corners](https://usage.imagemagick.org/thumbnails/#rounded).
  - Soft shadows with `-shadow` and `-layers merge`: [Generating Shadows](https://usage.imagemagick.org/blur/#shadow). The same page warns that `-shadow` grows the canvas by twice the blur and shifts offsets ("Shadows and the Offset Problem").
  - Composite over a backdrop with `-composite`, and fit a backdrop with `-resize WxH^ -gravity center -extent WxH`.
- **Input and output.** Any common image format in and out, including PNG with alpha and WebP.
- **Install.** `apt-get install imagemagick` on Debian (version 7.1.1 was used here, command `magick`). Also Homebrew, winget, and it is preinstalled on GitHub's Ubuntu runners (not verified here, see below).
- **License.** The ImageMagick License, a permissive license its site describes as "Compatible with the GPL v3". Source: [imagemagick.org/license](https://imagemagick.org/license/). It is a build tool here, not shipped in the repo, so nothing needs to be recorded beyond naming it.
- **Fit for Hyaline.** Full. It is the only tool surveyed that takes a real capture and does every framing step.

### Tools that capture a GUI

These belong to the capture tickets, so only the basics are recorded here.

- **shot-scraper** (Apache-2.0, `pip install shot-scraper`): "automated screenshots for documentation, built on Playwright". Web pages only. Source: [README](https://github.com/simonw/shot-scraper/blob/main/README.md). Hyaline's preview page already uses headless Chromium directly, which does the same job with one less dependency.
- **Puppeteer and Playwright**: what Catppuccin's vscode-icons workflow and shot-scraper use. They screenshot browser pages. Whether they can drive Electron apps such as VS Code for a port was not checked here.
- **scrot** (MIT-style license, [COPYING](https://github.com/resurrecting-open-source-projects/scrot/blob/master/COPYING)), **maim** (GPL-3.0, [COPYING](https://github.com/naelstrof/maim/blob/master/COPYING)), and ImageMagick's `import`: grab an X11 display or one window. These are the usual way to shoot a real app in a virtual X server in a container.
- **Nothing found** that automates real GUI screenshots for a theme project end to end. That part of the pipeline is new work.

## A tested ImageMagick recipe

Run here with ImageMagick 7.1.1-43 on two 1280x960 captures and `wallpapers/white-sands-dunes.jpg`. Values (padding 96, radius 14, shadow blur 24, drop 16, opacity 0.45, gap 64) are placeholders for the later ticket to pick.

Single image, one variant:

```sh
w=1280; h=960; pad=96; r=14; cw=$((w + 2*pad)); ch=$((h + 2*pad))

magick wallpaper.jpg -resize "${cw}x${ch}^" -gravity center -extent "${cw}x${ch}" -gravity northwest \
  \( -size "${cw}x${ch}" xc:none -fill "rgba(0,0,0,0.45)" \
     -draw "roundrectangle $pad,$((pad+16)) $((pad+w-1)),$((pad+16+h-1)) $r,$r" \
     -blur 0x24 \) -geometry +0+0 -compose Over -composite \
  \( capture.png -alpha set \
     \( -size "${w}x${h}" xc:none -fill white -draw "roundrectangle 0,0 $((w-1)),$((h-1)) $r,$r" \) \
     -compose DstIn -composite \) -geometry "+$pad+$pad" -compose Over -composite \
  framed.png
```

The three layers, back to front: the wallpaper cropped to the canvas, a blurred dark rounded rectangle as the shadow, and the capture with its corners masked.

For a Dark and Light pair, widen the canvas to `2*w + 2*pad + gap`, draw both shadows, then both windows.

What the test showed:

- **The window interior is unchanged.** Cropping the window back out of the framed image and comparing it with the capture (`magick compare -metric AE`) gave 0 differing pixels once the crop is inset by the corner radius. Over the full window rectangle, 228 pixels differ: exactly the four masked corners.
- **Corners do remove pixels.** Rounding cuts about 57 pixels per corner at radius 14. If "pixels inside the window are never altered" is read strictly, the radius must match the app's own window corners, or the corners must stay square.
- **Place layers at explicit coordinates.** The first attempt used `-shadow` with `-layers merge` and centered the result. The shadow's larger canvas shifted the window, as the usage guide warns. Drawing the shadow on a full-size canvas avoids it.
- **Draw every shadow before any window.** In the pair, the second window's shadow was first drawn after the first window and darkened 10,142 of its pixels. Shadows first, then windows, brought that to 0.
- **Do not resize the capture.** Any resize alters every pixel. Fix the capture size in the capture step and let the canvas size follow from it. Output sizes here: 1472x1152 single, 2816x1152 pair.
- **Save as PNG.** JPG and lossy WebP change pixels. PNG and lossless WebP do not.

## What Hyaline can reuse

| From | Reuse | License |
|---|---|---|
| ImageMagick | the framing tool: backdrop, padding, corners, shadow, pair | ImageMagick License (permissive). A build dependency, not copied into the repo. |
| The recipe above | a starting point for the framing script | written here, MIT with the repo |
| Catppuccin | conventions: one file per variant, same size, combined image on top. The CI shape: render, frame, open a PR with `peter-evans/create-pull-request`. | ideas only, nothing copied |
| Dracula | a fixed sample file per app, so every variant and every retake shows the same content. Crop to the window. | ideas only. The `sample/` files are MIT if ever copied, with credit. |
| freeze, vhs | their flag names as a checklist of framing knobs (margin, padding, radius, shadow blur and offset). vhs's one-script-per-recording and Docker image. | ideas only |
| catwalk | the `composite` layout idea (one window, split between variants) | idea only. The tool itself does not fit two variants. |

Not reusable: freeze, vhs, silicon, termshot, Carbon, and ray.so as tools. They draw their own picture of code or a terminal, which the map rules out ("Real apps, really themed. Never a mock.").

## Not verified

- **crates.io** returned HTTP 403 with an empty body, so the crate names `catppuccin-catwalk` and `silicon` come from the READMEs, not the registry.
- **Rosé Pine Images.** The social image app's source repo was not found under the `rose-pine` org by name. Only its link in TODO.md was seen.
- **How each project's maintainers take their screenshots in practice** (OS tool, window size, wallpaper). No project writes it down, so it stays unknown.
- **Whether other Catppuccin ports automate previews.** A code search of the org for `catwalk` in workflow files and justfiles found only vscode-icons and plymouth. The org has hundreds of repos and the search returns a limited sample.
- **ImageMagick on GitHub's hosted runners** (Ubuntu, Windows, macOS) was not checked. The runner research ticket should confirm it or plan to install it.
- **ImageMagick on real window captures.** The test used the preview page captures, which already contain a wallpaper. A capture of a native window with its own rounded corners or transparency was not tried.
- **Playwright or Puppeteer with Electron apps.** Not checked.
- Image sizes are from one port per project and are examples, not rules.
